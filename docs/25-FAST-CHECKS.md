# 开发、测试与提交

## 日常流程

1. 核对 `git status --short --branch`、HEAD 与任务范围；保留他人改动。读 HANDOFF、TASKS 条目及相关组件。
2. 功能任务先复现或核对来源，再做最小实现；规划任务只改文档。改数据前保存两包哈希与对象基线。
3. 按下表跑相关检查；一次差异审查覆盖需求、规则和调用关系。发现问题只补相关测试与复查。
4. 功能变化做对应浏览器样段；记录已测范围和缺口。更新 HANDOFF/TASKS，审查暂存差异后用英文祈使句提交。

默认在 main，不固定双代理、不重复确认、不为每个小改动重跑全城验收。只在相关源码、依赖、配置和需求均一致时复用检查结果。

## 检查选择

| 改动 | `--scope` | 浏览器 |
| --- | --- | --- |
| 文档 | `docs`，仅空白检查；人工核链接和事实 | 无运行行为变化时不需要 |
| 控制/驾驶/碰撞 | `controls`，路面变化加 `roads` | 修改模式、失败恢复及接触样段 |
| 地形/道路/桥面 | `roads`，生成器变化加 `data` | 接缝、上下层、实际通行 |
| 建筑/地标 | `buildings`，影响地面加 `roads` | 同机位画面，碰撞变化实走 |
| 树/灯/人/站口/无人机 | `street`，补实际依赖 | 画面及完整运动周期 |
| 界面/加载/键位 | `ui`，驾驶联动加 `controls` | 交互、持久化及失败恢复 |
| 管线/共享包 | `data` 加消费者 | 首帧与受影响样区 |
| QA/服务器 | `tooling` | 只检查受影响工具 |
| 共享核心、格式/精度/坐标、大规模入口改动或正式发布 | `full` | 集成场景；发布走 10 号全程 |

```sh
python3 tools/qa/check.py --scope controls --list
python3 tools/qa/check.py --scope controls --scope ui
python3 tools/qa/check.py --scope docs
python3 tools/qa/check.py --scope full
```

名单由 `tools/qa/check.py` 人工维护，不是依赖分析；可用 `--node`、`--python` 补具体测试。运行器使用 `.agents/three-0.187.0`（或 `SZ_THREE_PACKAGE_DIR`）和 `.venv/bin/python`，Node/Python 各跑一次。拒绝缺依赖、空跑、跳过、失败与运行期间源码变化。直接 `node --test` 不包含 Python 管线检查。

结果写本地 `docs/qa/checks/<时间>/result.json`，含 HEAD、源摘要、版本、测试名单/数量/耗时；不会替你确认浏览器或审查通过。`docs` 是 `whitespace-only`；文档若被现有测试读取，还需运行该定向测试。

## 浏览器与证据

- 用 `python3 tools/sz/serve.py --port 8080`，打开回环地址；已有合适服务可复用。启动成功要同时看到首帧、加载层隐藏、真实输入生效。
- 普通检查复用页面；加载/缓存/入口/引擎变化才冷启动。冒烟等待设上限，建议30秒；一次有依据的环境恢复仍失败，就记录并转专项诊断。
- 保存原始错误。既有错误只能在相同相关代码/引擎/配置下对照，不能写成“无错误”。不得用直接写坐标代替实际输入验收。
- 日常只验修改范围；冷热各5次、完整路线和20分钟稳定性留给性能/发布任务。结束恢复普通地址、界面和相机，清理本轮临时服务。
- 每次本地证据只需：任务/基线、测试结果路径、浏览器环境与实际区段、截图/错误、审查结果、剩余限制。状态统一 L1–L5，详见10号。

## 提交与里程碑

文档改动不触发功能发布。日常相关检查和审查通过后提交；推送前检查 `git diff --cached` 的大文件和本机路径。正式里程碑须满足10号全部相关条件，更新 HANDOFF/TASKS，再提交、推送并打 `baseline/m<N>`；自动测试通过不等于里程碑完成。
