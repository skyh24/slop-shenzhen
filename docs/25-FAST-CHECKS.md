# 功能开发的快速测试、审查与提交

2026-11-11 用户确认：每个功能完成后，快速测试、审查并提交；大版本再统一全量验收。本文是本仓库检查频率、范围和结果复用的唯一入口，适用于开发、审查、合并及通用技能调用。正式质量目标仍见 [11 号](11-MVP.md)，完整验收标准见 [10 号](10-PERF-QA.md)。

## 1. 每个功能的最短闭环

1. 开工时记录任务分支、基线提交、需求及受影响模块。先读 HANDOFF 当前状态、CONVENTIONS 和对应模块要求；其他规划仅在涉及该项时读取。同一会话不重复读取未变化的文档。
2. 开发中只跑正在修改的行为测试。缺陷修复优先复用失败用例；新用例应证明用户可观察的行为，不为每处改动机械增加测试。
3. 完成后选择下表范围，一次运行相关回归；涉及页面行为时，再执行一次对应场景检查。测试名单需包含本次新增用例和直接调用方。
4. 对当前差异审查一次，检查需求、正确性、集成与仓库硬规则。修复发现后只重测和复查受影响部分；没有新改动、失败或新证据就结束检查。
5. 用 `git diff --cached` 检查实际提交范围、敏感内容和产物大小，提交本任务文件，英文祈使句说明变更。普通功能通过后直接提交，无需再问一次许可；推送、合并和发布按用户授权及里程碑规则执行。

普通功能的完成条件：相关回归通过、没有未处理的本次缺陷、需求边界明确、必要的浏览器检查有结论。缺失依赖、测试跳过或浏览器失败不能记为通过；可以保留明确标注为未完成的工作提交，不得宣称功能验收完成。完整里程碑仍须满足九条要求和实际路线标准。

## 2. 按影响范围选择检查

| 变化 | 日常自动测试范围 | 浏览器检查 |
| --- | --- | --- |
| 文档、注释、流程规则 | `docs`，检查差异与引用；改变脚本则加 `tooling` | 无需 |
| 控制、车辆、上下车、碰撞 | `controls`；影响道路/自动路线时加 `roads` | 修改的输入与一个正常/失败场景 |
| 地形、道路、桥面、通行 | `roads`；改生成器或共享包时加 `data` | 修改样段，含上下层/接缝和显示接触一致性 |
| 普通建筑、地标、楼名 | `buildings`；影响地面时加 `roads` | 修改对象的固定视角，碰撞变化时实际通过 |
| 树、灯、行人、车站、无人机 | `street`；影响碰撞/导航时补相应范围 | 修改对象或一段完整运动周期 |
| 菜单、键位、界面和加载提示 | `ui`；影响驾驶控制时加 `controls` | 修改的交互及相关失败恢复 |
| 数据契约、生成器、共享数据包 | `data` 加实际消费者；格式/精度/坐标变化用 `full` | 首帧及受影响样区，包变化检查数据与接触一致性 |
| QA/测试工具、开发服务器 | `tooling`，新增工具需自身行为检查 | 仅浏览器工具变化时检查它本身 |
| 共享核心、引擎版本、入口装配大改、跨模块重构 | `full` | 与改动相关的集成场景 |
| 大版本、里程碑或用户要求全面验收 | `full` | 按 10 号完整路线、冷热各 5 次、性能及 20 分钟稳定性 |

范围不明确时扩大到 `full`，不按修改行数判断风险。名单由 `tools/qa/check.py` 管理，**是人工维护的常用组合，不是自动依赖分析**；新增模块或间接依赖变化时必须补选。计划阶段的 00–10 号文档和历史验收数字不代替当前结果。

```sh
# 先看本次将跑哪些文件
python3 tools/qa/check.py --scope controls --list
# 多范围合并去重，额外补入新的用例
python3 tools/qa/check.py --scope controls --scope ui --node tests/controllers.test.cjs
# 数据或大版本检查
python3 tools/qa/check.py --scope data
python3 tools/qa/check.py --scope full
```

入口自动使用本地 Three 0.187.0（可用 `SZ_THREE_PACKAGE_DIR` 指定）和 `.venv/bin/python`，Node/Python 并行且各执行一次；缺依赖、空测试运行、任何跳过、失败或测试期间源码变化均返回失败。`docs` 只检查暂存/未暂存差异的空白错误，输出明确为 `whitespace-only`，文档内容和链接仍需审查。没有安装运行时依赖也能执行 `docs` 或 `--list`。

日志和 `result.json` 写入本地 `docs/qa/checks/<时间>/`，不提交。报告包含 HEAD、源内容摘要、运行时版本、测试名单、数量、跳过、耗时和退出码；浏览器与代码审查默认标为未运行/未记录，不能由脚本推断通过。该入口不重建城市包；仅数据输入或生成逻辑发生变化时按 HANDOFF 的单分支构建规则运行 `build.py`。

## 3. 审查一次，结果跟着代码走

日常由当前执行者完成一次差异审查，不固定启动两个代理。规范和需求是同一次审查的两个检查项，结论可以合并成简短报告。用户明确要求独立/并行审查，或复杂改动需要独立意见时，再按风险选择审查者；避免开发者、审查者、合并者重复执行同一套测试。

审查只覆盖本次变更及其调用关系，优先找错误、遗漏、回归和明确的仓库规则违例。已有工具验证过的机械规则不人工重复检查；命名偏好、潜在重构、无证据的代码气味记为非阻塞建议，不为通过审查扩大功能范围。范围内真实缺陷仍须修复。

审查输入由当前任务提供：用户需求/对应模块文档、基线 SHA、改动文件、测试结果和已知限制。没有 issue tracker 时直接使用本次需求，不要求额外安装技能或建立工单。未提交修改用 `git diff <base>` 审查，并单独检查本任务新增文件；纯提交范围用 `git diff <base>...HEAD`。只有 `...HEAD` 会漏掉工作区，不能用于未提交功能的最终审查。

每个功能在本地测试报告旁保留简短记录即可：

```text
需求/范围：
基线 SHA / 已审查提交或差异：
自动测试 result.json / sourceHash / 实际数量：
浏览器：不适用、通过、失败或未测；证据与原因：
审查：发现、修复和剩余限制：
```

`sourceHash` 覆盖 js/css/index、tests、tools、data/source 的现有内容，包括未提交和未跟踪文件。它只是测试时的快照，不是自动缓存，也不是需求/文档/环境不变的证明。复用结果须确认：相关源码/测试/数据一致、依赖和工具版本一致、审查范围及需求未变。浏览器结果还依赖引擎、设备和场景配置。

- 测试后仅更新交接说明：复查文档，复用运行结果。
- 快进合并到相同已验证内容：核对提交与源摘要，复用结果。
- main 有相关变化、解决冲突或重建产物：补相关集成检查；共享核心变化跑 `full`。
- 只修复一项审查发现：针对该项补测和复查；除非扩大了影响范围，不重启整轮审查。

## 4. 浏览器检查的停止条件

普通功能只做一次与风险相符的冒烟/样区检查。冷启动对照仅用于加载、缓存、入口和引擎变更；其余场景复用已启动页面。多次冷热启动、全城路线、长期运行只在完整验收或性能任务执行。改变材质、几何或显示/碰撞时仍须看画面并验证相应行为。

启动完成判据是加载层隐藏、首帧可见且输入实际生效；`__szBoot.state === 'ready'` 或 `__szQA` 函数存在都不足以证明可操作。每个动作等待明确状态，普通冒烟启动等待设上限（建议 30 秒，超出记录阶段）；发生异常时只做一次有依据的环境恢复，再失败就记录失败并转入专门诊断，不反复重载、换键名或重建浏览器空间。

既有错误只在**相同相关代码、引擎版本和配置**下与已保存的特征/次数比较；错误新增、数量变化或可见行为异常即重新检查。保留原始日志和待办，不把既有错误抹成“控制台无错误”。输入未到页面与控制器逻辑失败分开记录，不能用写内部坐标或直接调用成功方法替代实际操作。

`perf-sample.mjs` 仅用于专门性能测量，不再作为日常冒烟工具。它现有最长 4 分钟轮询、固定等待和环境变量传递问题尚未重写；需要该工具时先核实实际配置。后台约 30 Hz 的样本不作为性能结论。结束恢复普通地址、UI 和常规相机，清理本轮临时服务/页面。

## 5. 本次移除与保留

| 项目 | 处理和原因 |
| --- | --- |
| 每个功能固定全量、固定双代理、合并再重审一遍 | 从日常默认流程移除，按第 2、3 节触发 |
| Node 再调用 Python 的 7 个包装用例 | 删除三个仅包装的文件及 buildings/terrain/ground 中四个包装用例；原 Python 测试全部保留，由新入口直接调用一次 |
| 开发服务器两个源码正则测试 | 删除；改为 Python 真实 HTTP 检查：文件更新后内容变化、成功/404 响应禁止缓存 |
| 数据往返/坏包/来源哈希、地形接缝与接触、碰撞和导航 | 保留；属于真实行为保证，不因耗时或年代删除 |
| import map/入口可达性、QA 本机限制 | 保留；这些结构本身就是运行契约 |
| 只绑定内部写法的其他测试 | 触及模块时评估替换；有替代覆盖或功能确已删除才能移除，不批量删断言 |

直接执行 `node --test tests/*.test.cjs` **不再包含 Python 管线测试**；完整自动检查使用 `python3 tools/qa/check.py --scope full`。因此旧 Node 总数不再可比，以实际执行名单和行为覆盖为准。

## 6. 经验与后续维护

- 2026-11-11 上一轮记录：476 项 Node 约 7 秒、104 项 Python 约 0.3 秒；耗时大头是临时组织浏览器检查和重复上下文读取。它们是当时运行值，不是当前固定预算。
- 测试快也只在需要时运行。先缩短准备、等待和重复审查，再优化测试运行器；暂不引入复杂的自动依赖分析或测试缓存。
- 之前误用启动状态、错误的 loading 选择器，以及数字键未送达页面，制造了无效等待。复用已验证的观察点，环境失败单独记录。
- 每个功能最多更新 TASKS 对应条目和 HANDOFF 当前结论；同一测试数据详细写在一份本地结果中，其他文档只链接。历史记录保留日期，不逐份改写。
- 后续删除测试必须注明：原测试保证什么、为何过期/重复、替代保证在哪里。节约时间不能来自把未测事项写成通过。

本次落地验证：`--scope tooling` 6 项通过（约 0.17 秒）；`--scope full` Node 480 项（7.03 秒）、Python 110 项（1.062 秒）全部通过、0 跳过，源摘要在执行前后相同。Node 与 Python 并行，Python 数量包含管线 105 项和工具 5 项；这些是测试入口验证，不是城市浏览器或里程碑验收。
