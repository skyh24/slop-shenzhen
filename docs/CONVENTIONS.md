# 开发规范

所有参与者（人或模型）都按这份规范做。和其他文档冲突时，以这份为准；规范本身要改，先在 [HANDOFF.md](HANDOFF.md) 的变更记录里写明理由。

## 1. 语言

| 内容 | 语言 |
| --- | --- |
| 和用户的对话、文档（`docs/`） | 中文 |
| 新写或改写的代码注释 | 中文 |
| 标识符、日志、报错信息、测试名、提交信息 | 英文 |
| 玩家看到的界面文字 | 中文，集中放在 `js/sz-strings.js`，代码里只引用键名 |
| 数据文件里的字段名 | 英文；地名保留中文原名，另有 `nameEn` |

纽约原版已有的英文注释不批量翻译，改到哪一段再顺手改成中文。

## 2. 代码风格

沿用纽约原版：

- ES Module，`import` 一律写在文件顶部，不在函数里动态 `import()`。只有循环依赖才例外，要在旁边写注释说明
- 两个空格缩进、单引号、语句末尾加分号
- 不引入打包工具和 npm 运行时依赖；three.js 只从 `index.html` 的 import map 取，版本锁在 `0.187.0`
- 新模块按 [01-ARCHITECTURE.md](01-ARCHITECTURE.md) 的文件名放，一个文件尽量不超过 1000 行，超过就拆
- 对有限取值的 `switch`（立面类型、车型、移动方式等），默认分支要报错，新增取值时不会悄悄落到默认处理：

```js
default:
  throw new Error(`Unhandled facade type: ${type}`);
```

- 注释只写代码本身表达不出来的约束（单位、坐标系、为什么必须这样），不写“下一行做什么”
- 随机数一律用固定种子，相同数据每次加载结果一致；种子取实体 ID 的哈希

## 3. 坐标和单位

- 原点 `114.0545E, 22.5463N`（市民中心主楼），1 单位 = 1 米
- x 向东，z 向南，y 向上；不旋转坐标轴
- 角度用弧度。地理方位角以正北为0、顺时针为正；当前实体控制器heading按`x=sin(h), z=cos(h)`，0为南、π为北。接口处明确换算，禁止混用或旋转城市坐标轴
- 扩区不改原点；已有实体的坐标和 ID 不变

## 4. 数据

- 原始数据放 `data/raw/`，不进 Git；每份都在 `data/source/sources.json` 里记地址、日期、SHA-256
- 人工核对的数据只放 `data/source/`（`landmarks.json` 等），每条写出处和 `status`
- `js/` 下的生成文件（当前为`sz-city.json.gz`，共享JSON v2）只能由 `tools/sz/build.py` 生成，不手改
- 每栋楼都带 `heightSource`，取值 `landmark`、`osm-height`、`osm-levels`、`overture-height`、`overture-floors`、`globfp`、`estimate`，以及逐个公开资料核对的 `published`（必须写在 `data/source/building-height-overrides.json` 并带来源链接，构建报告记录原值）。估计值不能写成实测值
- 匹配不上就不配，不用“离中心点最近”硬配；有歧义的记进 `build-report.json`
- 运行时不联网取地理数据

### 地形高程真实性（2026-11-09 用户补充）

优先真实 DEM 和有来源的测量数据。不得为了外观虚构山高、羽化到零或将未建模地区默认压平。重采样与量化必须记录；缺数据和范围外返回未知，不冒充零米。DEM 年代与精度不能冒充实时测绘。当前Copernicus为DSM，不是裸地；派生工程面须有可靠约束、转换/拟合与不确定性记录。显示与接触共用实际活动表面（含铺装/平台/桥面），不能回退旧DSM。细则见12第11节与10号验收。

## 5. 建模

- 地标、车辆、飞行器都用代码程序化建模，不导入外部 glTF
- 车型只取国产车的体型和比例，不画任何品牌标志、不写品牌名
- 不使用 APEC 官方会徽，只用文字和配色
- 显示和碰撞来自同一份几何：地形三角面、桥面、街具都一样。摆放时的避让半径和碰撞范围分开定义
- 架空层、连桥、门洞按分段实体建，不把二维轮廓挤成全高实心盒子
- 树、车、行人、无人机、道旗都用实例化渲染

## 6. 验收

一个功能分五级确认，汇报时写到哪一级：

1. 数据里有
2. 生成器生成了
3. 挂进了场景
4. 浏览器画面里看得见
5. 碰撞、通行和画面一致，按实际操作走通

- 日常开发、审查、合并和结果复用统一按 [25-FAST-CHECKS.md](25-FAST-CHECKS.md)：相关测试和一次差异审查通过后提交；共享核心变更或大版本才跑全量。通用技能的固定全量/双代理流程按该规则适配。
- 每个里程碑结束时：`python3 tools/qa/check.py --scope full` 全部通过；浏览器冷启动无控制台报错；按 [10-PERF-QA.md](10-PERF-QA.md) 的路线走一遍，截图存 `docs/qa/<里程碑>/`
- 自动路线（脚本驱动的车辆、传送）要注明是自动的，不能当作人工游玩验收
- 验收结束后恢复成普通游玩页面：不留固定机位、隐藏界面、调试参数
- 只改文档不需要重跑整套测试；改了数据、几何、加载、交互才跑对应的回归

## 7. Git

- 主分支 `main`；每个任务一个分支，名字用 `m<里程碑>-<短名>`，例如 `m1-importer`
- 提交信息用英文祈使句，例如 `Add SZB1 encoder`；一次提交只做一件事
- 每个里程碑验收通过后打标签 `baseline/m<N>`
- 不提交 `data/raw/`、`.venv/`、`ref/`、密钥、本机绝对路径
- 推送前跑一次 `git diff --cached` 检查有没有大文件和本机路径

## 8. 文档

- 完成一项就把 [TASKS.md](TASKS.md) 里的 `[ ]` 改成 `[x]`，做到一半写 `[~]`
- 每次交接更新 [HANDOFF.md](HANDOFF.md)：当前状态、下一步、遇到的坑
- 调研得到的新事实写进 [RESEARCH.md](RESEARCH.md)，带出处链接
- 数字（楼栋数、路长、帧率）要写清口径和测量时间，不和旧数字混用
