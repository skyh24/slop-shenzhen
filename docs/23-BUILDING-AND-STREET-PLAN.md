# 23 建筑身份、城区地面、街道标准与出租车曲面

更新于 2026-11-12。第 1–3 节保留 11 月 10 日建筑诊断与当时的修复方案。第 4–9 节是本轮出租车和街道的实施计划，现状与计划分别记录。占道对象清单见 [18 号](18-ROAD-BUILDING-CLEARANCE-PLAN.md)，楼高来源统计见 [21 号](21-FOOTPRINT-AND-STREET-AUDIT.md)。

浏览器已复现福中三路这两栋楼，不再做存在性检查。截图在本地 `docs/qa/building-diagnosis/yinglong-road-and-needle.png`（该目录不进 Git）。地点牌显示香蜜湖路一带，前景是福中三路。

## 1. 两栋楼分别是什么问题

主要不是坐标整体偏移。是两个数据处理问题叠在同一段路上。当前裙房避让只约束后来外扩的裙房，管不到这两栋原始楼体。

| | 前景白色楼 | 右侧细高楼 |
| --- | --- | --- |
| 画面 | 楼体占住福中三路 | 底面很窄、竖得很高的杆状楼 |
| 底面 | Overture 补充轮廓，约 94 m² | 约 4.6 × 7.5 m |
| 高度 | 源数据没有楼高，程序估成 7.3 m，`estimate` | 118.5 m，来自另一块约 2,319 m² 的 GloBFP 轮廓 |
| 直接原因 | 与估算车行道重叠约 58.5%，加缓冲后约 74.6%，低于删除线 80%，被保留 | 严格同楼匹配没过，后备规则只因小轮廓被盖住一半以上就继承了大轮廓的高度 |

白色楼与**当前道路模型**的冲突已经确认。道路宽度本身是估算的（OSM 车道数或等级默认宽）。在核对近期影像之前，不能写成“现实中这里完全没有建筑”。细楼则是合并程序把两个对象拼成了一栋：渲染器按“小底面 + 大高度”挤出，就成了截图里的细杆。

换数据源能改善轮廓和高度的底数，代替不了修正这两条规则。

## 2. 代码上的两个口子

占道过滤在 `tools/sz/buildings.py` 的 `filter_misidentified_footprints`。面积小于 300 m²、又没有 OSM 对照轮廓时，车行道（半宽再加 1 m）覆盖比例达到 `CARRIAGEWAY_SHARE = 0.8` 才删除（第 37、254–256 行）。中心线已经穿过楼，重叠 58.5% / 缓冲后 74.6%，仍低于 80%，所以白色楼留下了。大于 300 m² 的补充轮廓、以及和 OSM 楼有任何相交的轮廓，这条规则直接保留。

高度在同一文件第 624–644 行。严格匹配要求交并比 ≥ 0.6、面积比 ≥ 0.65、中心距 ≤ 12 m（第 639 行）。细楼没有通过。紧接着的后备（第 643–644 行）只要求相交 GloBFP 盖住小轮廓面积的一半，再按重叠面积加权平均高度，记成 `globfp-overlap`。2,319 m² 的高度因此写进了约 35 m² 的底面。[02 号第 4 节](02-DATA-PIPELINE.md#4-建筑合并与楼高) 只写了严格匹配，没有写这条后备；现行包里它却是一大批楼的高度来源（21 号统计为 8,200 栋）。

Overture 官方说明机器识别会把车棚、集装箱、太阳能板当成建筑，并承认部分轮廓精度低。GloBFP 论文里中国验证样本的高度 RMSE 约 13.17 m，高层更散，这是总体指标，不是每栋楼的误差带。当前包 36,064 栋普通楼里，约 85.6% 的高度来自 GloBFP 或程序估算，够看城市轮廓，不够逐栋 1:1。

Overture 的东亚建筑上游和 GloBFP 的东亚轮廓来自同一研究体系。两边都有，不算两次独立核实，匹配时记成同一上游族，不能两票通过。

## 3. 建筑数据怎么改

先确认是不是同一栋楼，再合并属性。给一栋真实建筑一条稳定记录，角色分开：主楼、裙房、雨棚、连桥、未知。高度只绑到对应楼体。面积、形状、位置或父子关系对不上时，高度保持未知，不把整栋大楼的米数赋给小部件。

每条记录分开写轮廓、高度和年代的可信度：

| 字段 | 记什么 |
| --- | --- |
| 轮廓 | 来源、原始对象 ID、匹配依据 |
| 高度 | 来源、数值、匹配依据；未知就不要填 |
| 年代 | 影像或地图年份、核实状态 |
| 上游族 | 是否和另一来源共用同一套建筑数据 |

2026 年发布的数据包不表示影像也是 2026 年拍的。来源能追溯，才能改错而不改丢。

建筑和道路一起看。占道候选用同一时期的正射影像、实景或总平面判断：楼识别错了、屋顶偏移、道路位置或宽度错了，还是确有架空通道。确认之后改对应的数据和三维结构。不统一删楼、挪楼或缩窄道路。

先做深圳本地样本，再决定用哪套源。样本覆盖福田高层、科技园、城中村和立交周边，统计误检、漏检、轮廓偏差、楼高误差和占道。新源（含 GlobalBuildingAtlas 的轮廓、高度和 LoD1）必须在这同一批样本上比较。该图集影像主要来自 2019 年，解决不了深圳近年的变化，只能当候选。

冲突检查放在生成正式包之前：

- 自动检查只负责把异常列出来。
- 有依据的改正进核对表（现有 `building-height-overrides.json`、`building-footprint-reviews.json` 继续用，并补角色和占道结论）。
- 确认不了的进待核清单。
- 高度不确定：可以留明确标注的简化体量。
- 存在性不确定、并且阻断车行道：先不进正式场景。福中三路这栋白色楼在影像核对前按这一条暂缓，不把它写成“现实中不存在”。

第一批代码只做两件事，不换数据源：

1. 占道增加道路中心线穿越。中心线穿过补充轮廓，或按道路边界（仍要标明宽度是估算）重叠到妨碍行车，就进待核或暂缓，不再只卡 80% 面积。OSM 已标注的楼仍然不自动删。
2. 删掉“覆盖一半就继承高度”。保留第 639 行的面积比、交并比和中心距；尺寸不相称的候选保持未知，走 `estimate` 或待核，不再产生 `globfp-overlap`。

通过条件：截图里的细杆不再是 118.5 m；白色楼不再挡在当前车行道模型上，同时报告写明道路宽度来源和“未用影像否定该轮廓”。回归要包含一块真同楼（面积比、交并比都够）仍然能拿到 GloBFP 高度。

## 4. 城区地坪与分区铺装

普通城区以同一个水平地坪为目标。试点先从市民中心—福中三路的现有高程核对点选一个基准，办公、住宅、公共广场、商圈和地面道路接到同一条水平线上。普通街区内部不保留 DSM 的树冠、屋顶和碎波纹。样段需要接到已核实的不同标高时，在明确的连接带内用缓坡或台阶过渡，共享端点标高。桥面、隧道、已知台地、河岸和海面各用自己的表面。扩到一期前，核对沿海、山脚和已知工程标高，确认同一基准的适用边界。

现有 `tools/sz/road_surface.py` 会先按路段估纵坡，再把路边过渡回原 DSM。只调滤波或加宽过渡带会继续把原地面的局部起伏带回街区。沿用现有地形生成与三角采样，在生成阶段先解城区基准与共享边界，再从同一派生地面生成路面和铺装。建筑基底、人物脚底、车轮、碰撞、地图落点和街具接触都读取生成的表面。原始高程保留，工程派生值记录来源、处理范围和误差。首批只改样区。

- 复用 [27 号](27-REGION-DATA-PLAN.md) 的道路外缘围合。办公、住宅、公共设施及商业分别圈出，商圈可跨多个地块关联，路和立交保留独立走廊。
- 商圈内部按地表实况拆分石材铺装、广场、步道、草坪、花池及建筑前场。地图上的绿色作为核对线索。铺装已核实就按铺装，明确为公共步行面但材质待核时使用中性硬质外观并标估计；边界、用途或通行未知的区域留待核。
- 自然起伏只留在有依据的公园和山地；平地公园仍平。用已核实地形平顺采样，保留山脊和真实坡向，公园入口、山脚步道用连续缓坡接到城区地坪。路缘高差、入口台阶、无障碍坡道按各自表面建模。

验收用同机位前后图及实走覆盖“道路 → 办公前场或公共广场 → 住宅入口 → 公园边界”，另核对一个有铺装和绿化并存的商圈。查共享边界两侧采样是否接齐，记录纵断面、最大新增高差和过渡坡度；车轮与人脚贴合，建筑底部、入口和街具无明显悬空或埋入。

## 5. 立交和隧道

深圳已有 `js/sz-elevated-roads.js` 的桥面和部分可驾驶匝道，`js/sz-tunnels.js` 已有洞身和碰撞计划，正式入口当前只读取隧道审计清单。参考武汉 `js/runtime/tunnel-surfaces.js` 和 `tunnels.js` 的洞口、坡道、层身份与镜头处理，用深圳现有 `surfaceId`、碰撞和车行图接入，沿用已有桥面实现。

先验车公庙一条完整上桥及下桥路径，再选一处有公开资料、洞口和地面接点可配对的公路隧道。地面、桥面、匝道及洞内分别有可采样表面，只在连接点换层。隧道口局部裁开地形，洞顶保留上方地表，洞身有墙、顶、铺装与照明，护栏、桥墩和墙体的显示与碰撞一致。标高或净空缺失时先核对，估计值写明来源。无依据的中心线穿楼保留在净空核对清单。

验证地面 → 匝道 → 桥面 → 地面，地面 → 进洞 → 出洞，以及同坐标桥下和隧道上方。手动驾驶先走通，再核对导航、自动驾驶及环境车流；相机进出无穿顶，车辆不上错层，地面车不会被吸进隧道。

## 6. 深南大道绿带与路侧

先把车公庙到红树林路的代表性样段做完整，再按有来源的路段扩。主路中央以两幅车行道之间有证据的范围生成实体绿带，沿用 `tools/sz/road_frontage.py` 和 `js/sz-road-frontage.js` 的走廊、三角面及接触。车公庙已有核对过的分隔范围和局部路缘、灌木；`07e6100` 已有草层、乔木及双侧／单侧放置候选，需整合后复核效果。样段包含路缘、地被草、成组灌木和乔木，层次及种植开口按资料校对。无逐株来源的株距、冠幅和品种作为外观估计记录。保留路口、掉头口、匝道口及过街断点。

路侧参考武汉的连续路缘、抬高人行道和入口台阶。大路按左右两侧布置树和路灯；窄小路或单向支路默认选一侧，优先跟随已有的人行道、建筑入口和净空，车行方向另按路网资料。有人行道来源时优先画真实范围。过街与无障碍入口做降缘或缓坡，台阶只用于确需高差的入口。树池、灯杆与设施沿路缘布置，避开车道、出入口、过街位置和人行通道。先用深南主辅路和一条小路检验双侧与单侧，白天步行过街并在夜间核对两种布置。

## 7. 道路断面与标线

道路以现有 OSM 路网和已核实的道路走廊为输入。复用 `js/sz-roads.js` 已生成的车行道边界、路口范围和实际行驶线，用同一断面组织行车方向、车道宽度、边线、路缘和绿带。路面、车流及标线需要同一份路段与表面身份；路侧设施从同一边缘布置。宽度、车道数和分向优先用可靠来源，缺失时标记估计。

当前 `js/sz-road-markings.js` 已做分段偏移、弯道斜接及信号进向剪裁。剩下的缺口是部分规则只看单条地面链路：偏移仍可按整条宽度对称推算，只有带信号的进向会剪纵向线，短链按图节点度数可触发封口线。先在深南大道和红树林路路口逐条复现，再用实际车行道和路口范围约束标线，核对主辅路并行、分合流、无信号路口及折返，不另做一套道路网。

| 断面 | 标线规则 |
| --- | --- |
| 物理分隔的双向大道 | 两幅各按单向布置，白线分同向车道，内外边线贴各自路缘。草带中央没有车道线，绿带开口单独处理。 |
| 未物理分隔的双向路 | 在可分向的位置使用对应黄色中心标线，同向多车道按资料画白色分车道线。已有资料能区分实线、虚线时按资料。 |
| 单向路、窄支路和住宅街 | 单向多车道才分道。窄路或车道资料不足时收敛线量，根据宽度和资料确定是否画边线或中心线。 |
| 路口、出入口、匝道 | 纵向标线退出冲突区。按信号、让行、已核实过街设置停止线和斑马线，同一进向各画一次。无来源的封口线移除。匝道按合流、分流及实际导流范围留白。 |
| 桥面、隧道 | 沿用同一套线型，用各自的路面三角形定位。上下层投影重叠时，线只出现在所属路面。 |

按已有深圳道路设计资料与样段实景核对线宽、颜色、虚线节距和适用条件，再把选定值写进配置。先查一处弯道、一处窄单行、一处普通路口和一处主辅路汇合。标线完整宽度不得跨路缘，重复标线、穿过路口的纵向线、飘在空中的线、误画在匝道下方的线都应为零。白天、夜间和湿路面均可读。

## 8. 深圳出租车车身曲面

用户截图中红线沿左右尾部轮廓标出希望连顺的位置。保留约 1.73 m 高车顶、宽长后舱、较直立的尾门、深色环绕车窗和蓝白深圳涂装。调整重点是从车顶、后窗柱经腰肩到尾门和后保险杠的截面，保留有辨识度的后舱体量。

现行 `js/cars.js` 分开生成下车身与玻璃房，腰线处可能发生转折或接缝处高光跳变。先用深圳出租车的后部截面检查两者的相交、宽度和法线；让上段与下段在腰线共享边界并对齐切向，圆角从后窗柱连续过渡到后翼子板和保险杠。沿用现有 loft、玻璃和灯具材质。必要时只将这段外皮共用顶点和法线，窗框与尾门缝继续用材质和细节表达。玩家和环境出租继续共用一份深圳模型。

用正后、侧后 45° 和正侧的日夜近景验收。正后沿用户红线检查轮廓，侧后看高光是否连续，正侧看高顶与后舱比例。检查窗边无裂缝、尾灯贴合、轮胎满舵不穿轮拱，座舱和车体碰撞边界仍匹配。单独执行车辆检查，可与地坪试点并行。
