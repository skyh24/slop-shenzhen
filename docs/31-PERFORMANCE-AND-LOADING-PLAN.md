# 性能与加载优化方案

更新：2026-11-13。本文包含 S2 数据压缩设计（第1–7节）与 S4 启动/区域加载研究（第8节），不是优化完成报告。两个实施批次分开；最新排查顺序以第8节为准。用户要求：只做有明显收益的优化，以关键数据和最终审查为主；实施提示词放对话，不放 TASKS。当前状态见 [HANDOFF](HANDOFF.md)，工作状态见 [TASKS](TASKS.md#网站体积与启动专项sol-61)。

## 1. 当前事实与目标

本次读取基线为 `a61768e`；工作区另有建筑外墙、相机、无人机和地图等未提交改动，实施前重新确认 HEAD、工作区和包哈希，不能拿其他任务的变化充当优化收益。

| 指标 | 本次读取值 | 用法 |
| --- | ---: | --- |
| 默认 JSON gzip | 12,512,588 字节 | 压缩收益分母；不能继续使用旧 11,304,063 字节基线 |
| 解压后 JSON | 54,828,922 字节 | 说明表达成本，不等于浏览器内存 |
| 地表 `terrainSurface` | 28,434,323 字节 | 紧凑 JSON 字节，约占解压包 51.86%，主要优化对象 |
| 建筑 | 9,529,611 字节 | 已采用列式数组、0.1 米轮廓差值和枚举 |
| 道路图 | 6,657,647 字节 | 保留连通、桥隧、单行和转向信息 |
| 对照 SZC1 gzip | 12,640,321 字节 | 比默认包大 127,733 字节，不直接改成默认 |
| 对象 | 76,022 条建筑、24,392 条道路边 | 只作为当前核对值；优化不增删对象 |

JSON gzip SHA-256：`e461dfd39b2b54ed724c75a50cbda7ff805b0cf58722d9332a919b75e3595015`。SZC1 gzip SHA-256：`b40e47dbced8926c5a5f997ffbfdc3f640a911d55f33b1bf7c8b4a9558a3fde7`。地表字段等大小以紧凑 UTF-8 JSON 计算，不可相加推算 gzip 收益。

已合入：顶层旧 `roads` 移出运行包、地表验证后共享解码、隧道审核移出启动、本地版本资源与发布缓存。不要重新实现，不把它们计入本轮收益；渲染端为避免修改共享查询数据而保留的数组副本，不可当作无用重复直接删掉。

**S2 主要目标：默认城市数据实际传输字节减少超过 10%，画面、地理事实和接触不变。** 若基线仍为上表，最终包须小于 11,261,329.2 字节。首次必需的新增文件须一起计入；审计文件若仍被首页加载，也必须计入。

启动或内存是次要观察项。只有同条件总启动时间或整页可比较的内存指标减少超过 10%、且超过测量波动，才能另报性能收益。单个函数加速、单个数组变小、JSON 解压体积下降均不能代替整页收益。包缩小也不自动等于帧率提高。

## 2. S2 范围与取舍

只做运行数据表达优化，默认保留紧凑 JSON + gzip。先完成一个地表候选，有必要时合并少量无消费者审计字段迁出；达标就收尾。不引入数据库、JSONP、Worker、Service Worker、全城流式或新的运行时依赖，不改画质、人数、车辆数量和城市范围，不为了文件行数拆代码。

| 对象 | 允许的处理 | 必须保持 |
| --- | --- | --- |
| 地表顶点与三角形 | 规则数据省略、差值、模板与例外、无损恢复 | 数值精度、三角形及绕向、顺序/索引语义、地类、孔洞、边界、裁切与采样结果 |
| 建筑轮廓/高度/立面/部件 | 原编码保留，必要时无损字典或整数编码 | ID、内院、底部高度、层数、角色、地标绑定、名称、heightSource |
| 建筑来源与可信度 | `upstream`、`fpConf`、`hConf`、`eraConf` 仅在确认无运行消费者后迁至审计文件 | 按稳定 ID 完整恢复；未知仍为未知；来源记录不可删除 |
| 道路图 | 重复字符串字典化，显式编码默认值和布尔值 | ID、连接、折点、宽度、车道、方向、桥隧层级、转向限制、名称和来源含义 |
| 道路 `lengthM` | 仅当无运行消费者时考虑迁出 | 审计原长度保留；几何重算长度不冒称与原值完全相同 |
| 地形 `terrain` 与活动面 `terrainSurface` | 分别保留 | 用途不同，不能因看起来重复而直接删一份 |

`widthSource`、`heightSource`、道路/节点 ID 已有实际消费者，不属于可随手删除的备注。默认值编码必须区分“未知”“不存在”和明确的 false/0。建筑审计字段是否迁出以执行时的调用检查为准，不根据历史检索结果直接删列。

## 3. 地表编码设计

### 当前内容

500 米分块、25 米基础网格；海岸、内河、铺装和排除区会产生额外顶点。`positions` 保存局部 x/y/z，`indices` 保存三角形顶点索引，`cellRanges` 保存格号/索引起点/索引数量，`kinds` 保存普通地面/绿地/湿地/铺装。

此前包约 89% 顶点位于规则网格、约 69% 顶点高度为 8 米，只是方向性证据；当前包需重新统计，不能推导为同等比例可删三角形。生成器已经按位置和铺装属性去重；不能把必要的颜色边界顶点合并。

### 主候选：保持原数组语义的紧凑列

优先减少表达冗余，不改三角剖分：

1. `positions` 分开编码水平位置与高度。对能够精确恢复的规则网格点，只存网格索引；其他点按原精度保存。高度使用默认值加例外，或连续重复值编码，选实现更简单且实际 gzip 更小的一种。
2. `cellRanges` 的 start 可由前项 count 累加恢复；cell 可存增量。保持原单元顺序、索引数量和查找语义。
3. `kinds` 使用默认类别加例外或连续值编码。保留铺装边界和同坐标不同地类的顶点。
4. `indices` 优先保留。仅在结构明确且能精确恢复时做简单差值编码；不要为了降低文本长度增加复杂压缩库。
5. 一次解码还原现有内部结构，再交给已共享的地表入口；不要让地面、空间查询、高架、隧道各自解析新格式。

候选是一个整体，不要求每一列都换编码；不盈利的列保留旧表示。JSON 中编码后的数字可能反而增加文本长度，最终以整个 gzip 包为准。

### 唯一后备：规则单元模板加例外面

主候选整体未达门槛，且统计证明规则单元的重复索引仍是主要体积来源时，再试一次模板方案。规则单元省略固定连接，裁切/铺装/海岸/排除区保留显式三角面；同一解码边界恢复旧数组及查询行为。无法无损恢复原顶点编号、三角形顺序或数值时，将该单元标为例外，不重新三角剖分。

不通过四舍五入边界、把 Float64 改成 Float32、降低高度精度或增大网格间距达标。不能把“画面看不出差别”当无损证明。

最多两个结构候选；不遍历所有格式、压缩等级、字段排列或库。主候选达到目标且无回归就停止，不再做后备。

## 4. 实施阶段

| 阶段 | 工作 | 进入下一步的依据 |
| --- | --- | --- |
| A 基线 | 锁定源码与包；读取已有计时，记录整个包及地表大小、对象摘要和当前可启动状态；列消费者 | 已有可复现基线，没有混入他人变化 |
| B 候选 | 在本地 QA 临时输出制作主候选；只做整包压缩、一次完整解码等价和少量解码计时 | 实际整包减少 >10%，数据等价，解码没有明显变慢 |
| C 条件补充 | 仅在必要时合并审计字段迁出；或采用唯一后备地表方案 | 明确可达目标；不是逐个追逐小于10%的改动 |
| D 接入 | 将胜出方案接入 build.py、读取/校验、快包兼容与报告，统一生成正式双包 | 格式声明一致，正常加载只取选定默认包，可回退 |
| E 最终收口 | 一次相关全量检查、一次浏览器样段与关键数据对照、一次最终差异审查 | 有效收益、等价与最终状态都有证据；或明确保留旧默认 |

基线阶段不重新构建地理数据；候选阶段不反复运行完整 OSM/建筑/地形管线。只用固定包做编码对比。正式产物只经 `tools/sz/build.py` 生成；必要时增加明确的重新编码入口并保留来源/快照校验，不能把现有 `--repack-existing` 冒充已支持新操作。写正式包前核对没有其他构建者同时工作。

### 接入需要覆盖的边界

- [build.py](../tools/sz/build.py)：默认格式、正式双包、报告、重编码入口与源摘要保持一致。
- [sz-data-format.js](../js/sz-data-format.js)：新版本/地表编码标记、长度/范围/例外索引校验、旧包可识别或明确报错；不能改变格式后继续冒用旧声明。
- [sz-ground-surface.js](../js/sz-ground-surface.js)：继续复用单套验证后数据及既有渲染复制边界。
- [fastpack.py](../tools/sz/fastpack.py) 与既有 JS 读取器：两种容器承载一致语义；SZC1 继续本机对照，不因格式修改自动转为默认。
- [sz-geodata.js](../js/sz-geodata.js) 与现有启动失败入口：保留缺包、坏包和重试，不加默认双包下载兜底。
- 审计字段如迁出，生成带版本、来源快照和稳定对象 ID 的独立审计产物；审计/构建校验从该产物读取，不让正常游玩加载。允许差异列表只列字段路径及去向。
- 复用已有发布白名单与版本路径，确保新旧代码/数据不混用；只调整本轮格式所需部分，不重写缓存系统。

## 5. 关键数据与验证安排

### 必须记录的少量指标

| 指标 | 记录方式 | 判定 |
| --- | --- | --- |
| 默认包及首访必需数据字节 | 同一压缩配置；新旧包 SHA、字节、新增必需文件 | 本轮主要目标，整体减少 >10% |
| 解压/解析/解码时间 | 同环境、同输入，基线和最终各3次，逐次及中位数 | 仅作为解码回归检查，不代替总启动收益 |
| 总启动到可输入 | 浏览器可用时，基线和最终各3次同条件冷加载 | 包括首帧、加载层退出和真实输入；不把初始化挪后隐藏耗时 |
| 数组/资源与内存 | 复用已有可测指标，报告口径 | 能测整页才声称整页收益；拿不到则明确未测 |
| 内容等价 | 一次全载荷语义对比，审计迁出走允许差异列表 | 建筑、道路、地表、身份及来源没有非预期变化 |

3次是本轮工程判断，不作为正式发布的统计验收。若只做包体优化且内存口径不可得，不搭建新的监控平台；不报告内存改善。时间明显变慢或样本波动足以改变结论时，只对该指标补一组3次；仍不能判断就注明不确定，不无限追加测试。

基线与最终的设备、浏览器、视口、相机、时段、种子、人数和画质相同；缓存策略及服务配置不变。冷 HTTP 缓存不等于冷 GPU 缓存，要分别记录。本轮不改缓存时，不额外做多组热缓存实验。所有指标排除其他并行任务的代码/数据变化。

### 必须保证的正确性

一个聚焦的编码回归覆盖：完整往返等价、规则与例外混合、空/纯例外块、畸形长度和越界、未知编码版本。复用已有基础设施，不为每个字段复制一套测试。

全载荷对比应验证恢复后的数组值、顺序、索引和地类，以及建筑/路网字段。几何一致性不能只靠随机高度点抽查；另选网格边、山脚、海岸、铺装边和孔洞点检查采样结果及无地面返回值。来源审计必须仍可按 ID 完整恢复。

### 集中在最终版本做一次

1. 格式/共享数据有改动，按仓库流程执行一次 `python3 tools/qa/check.py --scope full`；不每提交一次就全量。只改文档则不跑代码测试。
2. 同机位前后截图，固定短路线覆盖平地、山脚/坡面、铺装边、海岸或孔洞、分块边；复用桥上/桥下样点检查分层。真实走动/驾驶并检查模式切换。只覆盖格式影响，不复验全城所有功能。
3. 日间和夜间各一个代表机位；一个约60秒固定移动样段观察帧时与首次卡顿。若不动资源生命周期，不强制20分钟漫游；只有发现持续资源增长等证据才追加针对性长测。
4. 坏包/未知版本/重试主要由现有自动测试覆盖；浏览器不重复制造每一种错误。
5. 最后一次差异审查：遗漏消费者、数据丢失、版本兼容、额外副本、共享数组被修改、默认加载路径及审计字段是否仍被首页下载。修复后只复查受影响范围；共享契约再次变化才重跑相应全量。

这替代旧规划的“每项单独对照/测试/提交、冷热各5次、固定多场景长测”日常要求。[10号](10-PERF-QA.md)仍用于用户明确要求的正式验收或发布，本轮不宣称达到其全城标准，不发布公网。

浏览器若仍卡在 WebGPU 初始化：一次有依据的恢复仍失败就停止浏览器重试，继续离线等价与体积工作。保留候选为非默认，报告运行验收未完成，不绕过最终运行门槛，也不把引擎排障扩展成本轮长期任务。

## 6. 停止条件与交付

- 主候选整体超过10%、等价成立、最终无明显回归：交付，不继续追逐额外1%–2%。解码或总启动重复出现超过10%的退化时，不切默认；不足10%但新增可见卡顿同样不得忽略。
- 最多两个结构候选仍未超过10%：保留原默认，撤回本轮无效运行改动，留下一个简短结果。不要通过删除真实对象、降低精度或扩大项目范围凑收益。
- 等价失败：只定位与修复该编码问题；不能把测试改成接受丢失的数据。若无法修复，不接入默认。
- 初步体积达标但运行无法验证：只交候选与缺口，不能把“候选已生成”写成“优化完成”。

最终只交一张表：基线/最终包字节及哈希、缩减率、解码与总启动中位数（未测标明）、数据等价、最终检查、剩余限制。报告采用的编码、迁出字段及回退方式；不提交所有候选和过程日志。

本地证据放 `docs/qa/site-cost/`，不提交。只维护 HANDOFF 当前结论与 TASKS S2 状态，必要时更新本方案的最终决定；实施提示词不写入 TASKS。保留他人未提交改动，只提交本轮文件/片段，不建新分支或工作树、不启动其他 agent、不推送或部署。

## 7. 技术选择与后续条件

| 方案 | 重新考虑的条件 |
| --- | --- |
| Brotli HTTP 传输 | 当前结构已精简，实际传输仍是主要成本；配合现有 gzip 加载器修改与服务器解码，不能只改后缀或二次压缩 gzip |
| 二进制数值块 | 上述表达改进后，相同数据证明二进制明显更小/更快；不直接推广当前更大的 SZC1 |
| 分块按需加载 | S4 先按范围创建场景；网络拆包仅在下载/解码仍是瓶颈时进入，见第8节 |
| 构建端数据库 | 源融合与增量查询需要；不是本轮减包前置 |
| 浏览器数据库 | 产生复杂离线查询/编辑需求；引擎和存储管理成本有实际回报 |
| JSONP | 不采用；它是脚本回调加载方式，不是压缩格式 |

参考：[HTTP 压缩](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Compression)、[SQLite 浏览器加载](https://sqlite.org/wasm/doc/trunk/demo-123.md)、[JSONP](https://learn.jquery.com/ajax/key-concepts/)。当前技术选择基于本项目静态读包方式，后续需求变化再评估。


## 8. 启动瓶颈与区域加载研究（2026-11-13，S4）

### 8.1 结论与证据口径

先优化滨水、地铁出入口、无人机的初始化查询，再做按范围创建/释放；仅压缩城市包不能解决当前本机的主要等待。现有可见性剔除、模型实例化、近景 LOD 和局部人车池应复用。

本轮只读代码、当前包及已有 QA，未启动新浏览器、运行全量或重建。电脑近期存在多场景与构建并行的负载，已有短窗不能归因成单个代码改动的收益。样本没有完整绑定当前工作区摘要，以下是近期正式入口的排查证据，不是本轮冷启动或全城验收。

| 场景剔除初始化 `culling` | 1.79秒 | 1.79秒 | 建好全城后再拆批次/建阴影代理，也有一次性成本 |
| 道路标线 `build.paint` | 1.39秒 | 1.44秒 | 按道路范围分批生成候选 |
| 树木 `build.trees` | 1.30秒 | 1.34秒 | 模型已共享，但全城点位筛选、避让、实例创建仍提前执行 |
| 人群初始化 `build.pedestrians` | 1.20秒 | 1.20秒 | 密度/障碍资料和初始局部轨道，不是全城逐人模拟 |
| 道路 `build.roads` | 1.19秒 | 1.23秒 | 与标线分开记录 |
| 普通楼体 `build.blocks` | 1.06秒 | 1.40秒 | 局部代码含未提交修改；不能套用到所有版本 |
| 地标模型 `build.landmarks` | 0.26秒 | 0.28秒 | 不含独立园区/车站等初始化；不代表其渲染和编译免费 |
| 数据下载至解码合计 | 0.38秒 | 0.59秒 | 本机样本，不能推断公网弱网下载速度 |

前三项 final 合计33.52秒，约为 ready 耗时的61.5%。这证明优先级，不承诺都可消除。`traffic` 总阶段约37.55秒包含树、灯、站口、无人机和滨水，真实 `build.traffic` 约0.30秒；不得把进度条“交通”误认成车流瓶颈。大阶段与子阶段不能重复相加；并行编译调用时间之和不能与墙钟阶段时间比较。

final 的10秒运行窗口约31.8 FPS、simulation 18.02ms/帧、render CPU 11.97ms/帧、GPU少量样本19.66ms，约1354次绘制、666万三角。其他同目录短窗约25.6–33.9 FPS。simulation包含场景更新而不只是人物AI；CPU/GPU有流水重叠，不能直接相加。资源计数约0.70GB不等于系统完整显存。帧率结论仍需独占负载下的一次固定样段。

### 8.3 哪些已经做了，哪些还值得做

| 模块 | 当前实现 | 下一步 |
| --- | --- | --- |
| 普通建筑 | 全量创建楼体/屋顶/碰撞；2.4km静态合批；`update()`为空 | 5km内按块创建正常楼体，远处轻量轮廓；近场才准备细节及精确接触；保留全城轻索引 |
| 建筑细节 | 200m块，650m内生成、850m外释放，阳台/空调约200–250m | 保留更近的现有范围；加入统一创建预算，不扩大到5km |
| 地标 | 全量规划、创建；自身复杂度和材质不同 | 地标身份/替代ID/高度元信息先可用；近场完整模型，远处低模剪影，不能因未创建专模又显示普通楼 |
| 树木 | 六种共享冠形、实例化；约180m近冠、900m外隐藏；启动仍遍历全体并创建批次 | 保留少量树种，按附近块创建/回收实例；2km只作驻留上限，不把可见距离从900m扩大到2km |
| 路灯/站口 | 已实例化与距离隐藏；站口仍全量规划和建模 | 2km内按块准备，保持现有更近文字牌LOD；站点索引全城可用 |
| 滨水设施 | 约275m内创建实例、335m外释放 | 已有动态资源机制；主要补初始化查询范围和局部碰撞索引，不能重复做一套流式 |
| 环境车 | 全城路网初始化，30辆实例池，约360m出生/430m外回收 | 保持局部池；按地域调整车型/密度，远区只存轻状态，不在每区再创建30辆 |
| 环境行人 | 上限140，约260m轨道区/220m回收/130m骨骼更新；按道路与建筑密度变化 | 保持现有半径；索引轨道源，减少每移动100m重建时的全路网扫描，做区域参数与池调度 |
| 动态场景 | 每帧调用多种update；部分内部已有距离/开关控制 | 逐模块核查真正执行的工作；远区停几何/骨骼/粒子更新，时间逻辑按绝对时钟恢复 |

树木的“只建一份再复制”已经通过 `InstancedMesh` 实现，普通 `.clone()` 不保证合成少量绘制调用。实例共享不代表所有实例没有位置上传、顶点、阴影和像素成本；优先减少驻留批次和每帧遍历，不先把六种树全部改成一种。依据：[Three.js InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html)。

### 8.4 推荐架构与距离策略

统一管理活动区域，复用已有空间索引、共享材质/几何、局部人车池和近景加载器。小接口负责更新关注点、准备目标区、检查接触就绪、释放退出区；每个模块只提供创建/更新/释放实现。不要新造全套通用引擎。

- **全城轻量资料**：覆盖/粗地形、建筑与地标ID和包围盒、地点名称、路网连通和转向规则。地图、远程规划、未加载区搜索不能消失。第一批仍读现有包，只优化运行时创建；网络字节不会因此减少。
- **5km正常楼体范围**：以当前视点/活动位置为候选，按相交分块加载。远区保留简化天际线与主要桥梁轮廓；高空视野按投影尺寸或粗LOD处理，不直接扩大完整模型范围。屋顶设备/招牌沿用近距离规则。
- **2km静态设施驻留上限**：道路精细标线、树灯、站口、设施和桥梁细节按需要分批准备；现有更近可见/创建范围保持。地面和桥的粗表面不能一起消失，长桥及上下桥接缝按连续结构处理，不按柱子中心硬切。
- **几百米动态区**：人车继续已有局部范围；2km是预取或场景资源范围，不是全部人车精确模拟半径。各地域共享池，区域规则控制密度、车型和活动，不能为每区复制整池。
- **提前准备与延后释放**：用速度和方向预测相邻块，离开内圈后保留缓冲，避免在边界反复创建。地标观察/无人机跟拍时区分玩家物理区与相机显示区，两者受总资源预算约束；退出观察可恢复玩家。
- **传送/高速进入**：先备好目标区地面、桥面、建筑碰撞与可站表面，再允许移动或切换。旧区在新落点成功前保留。加载失败保留旧状态，不能让人物掉到未创建的地面。
- **预算分批**：初始化首屏必需范围，后台按有限毫秒预算创建相邻块；所有模块共用预算，不让每个模块各占10ms。500m级索引块可与现有500m地表配合，渲染仍按材质合批；不把每栋楼变成一个draw call。切块要带相邻建筑组用于共墙/内院裁切并保证对象只渲染一次。
- **后台页面**：检查统一的暂停/恢复入口，让隐藏或用户暂停的预览停止渲染及非必要模拟。恢复重置帧时间，不补跑积压帧；列车/节目等按各自时钟语义恢复，避免多标签页持续发热。不能依赖浏览器一定会替WebGPU循环暂停。

资源释放须区分实例、分块几何和共享模板，引用仍存在时不销毁共享资源；实例从场景隐藏不等于内存释放。首屏之后出现的新材质/属性组合也要预编译或预热，不能简单删除预编译把卡顿挪到首次转头。

### 8.5 实施顺序：每批有一个整体收益目标

**P0：修初始化热点，先不重写全城加载。** 复用现有计时，只给三个热点各补2–3个子段，核定究竟是空间查询、放置、几何还是图集。已发现的候选：

1. `sz-metro-entrances.js::nearbyCollider` 对入口逐次扫全体碰撞体；先复用空间索引取局部候选，再保持原多边形和高度判断。整段12秒不能全部归给该循环，需子段计时确认。
2. `sz-waterfront.js` 的灯位避让扫描全体障碍，随后又把全部 `colliders + obstacles` 按32m网格展开，尽管只服务少数滨水路线。改为查询复用索引或只索引路线包络及必要缓冲；长桥/长条包围盒采用合适粗粒度/分段，不能制造海量空格条目。其既有275m实例加载保留。
3. `sz-drone-routes.js` 在初始化规划路线、筛障碍、按约2m间距采样地高，并尝试绕行。先只查路线走廊障碍、缓存同一快照下的静态查询；如仍重，再将未进入附近/未选择跟拍的路线延后准备。源路线和运营状态立即可查，跟拍前必须通过净空，不能删校验。
4. 只有数据、静态接触几何和生成器版本都能绑定时，才把稳定放置/路线预处理迁到 `build.py`；不能缓存基于旧碰撞体的结果。先解决重复工作，再选择是否离线化。

P0采用条件为同条件启动到可输入整体改善超过10%，且没有新增运行卡顿；不能只报单个函数快10%。三个热点若全部缩短一半，按54.48秒样本的纯算术上限估算可省约16.76秒；这不是承诺，依赖/转移成本必须扣除。达标即交付，再决定P1。

**P1：按范围创建场景。** 在P0后仍有明显创建/内存压力时，先选树灯/站口或普通楼体其中一个有证据的模块接入统一生命周期，验证跨块和传送，再扩到同类模块。5km/2km作为初始配置，不做多轮半径穷举；地图索引、天际线和局部人车范围保留。地标先分离替代关系与完整几何，路桥先分离导航与渲染/接触准备。

P1目标为启动、整页可测内存或固定样段P95帧间隔其中一项改善超过10%，其余指标不能明显退化；全城记录数保持，减少的是当前创建量。帧率受绘制/阴影/像素负载影响，不能用总模型数下降直接宣称FPS提升。

**P2：按区下载和动态计算调度。** 仅当前两批后仍受数据传输/解析或每帧更新约束，再做独立压缩空间包、来源/版本索引和预取；或为热点更新增加活动区/频率管理。路网规划、建筑邻接组、远景/搜索跨块身份必须连续。后台低频逻辑与近场接触精算分开，玩家物理、人车碰撞不随意降频。不要在本轮同时加入网络流式、Worker、数据库和渲染重写。

### 8.6 有限验证与交付

复用第5–6节的集中验证原则：每批基线与最终各3次同条件启动；最终一个固定街面样段与一个飞行/跨区样段，看P95帧间隔、绘制与创建/驻留计数。只在资源生命周期改动时加一次往返区域的资源回落检查。共享模块变化最终一次full与一次差异审查，失败后只补受影响验证。不逐字段测、不对每项反复审查、不固定冷热各5次或20分钟漫游。

运行样段使用一个城市标签页，避免与其他全量构建并行；不要擅自停止用户任务，无法排除竞争时标注受干扰并保留结论边界。前后包/源码不同或工作区持续变化时，不计算优化幅度。原始证据仅留本地QA，HANDOFF写当前结论，TASKS写S4状态，提示词在对话交付。
