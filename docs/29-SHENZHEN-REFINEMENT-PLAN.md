### 立交、隧道和交通线路

- 深南—车公庙—滨河以来源路网的方向和连接关系逐段核对。启动自动驾驶时检查车身所在层与路线起点层。路线规划按所选桥面查轮位、护栏、桥墩和车身净空。跨层只走明确连接，手动、自动和环境车辆分开验。下车位置与车辆同层并有可站立表面。
- 隧道候选来自 OSM `tunnel`、`layer` 和配对后的真实入口、出口。记录方向、洞口接地、坡度、洞顶和净空来源。资料足够时先做一个洞口和一段洞身，局部切地面并保留洞顶地表。无依据的中心线穿楼继续留在审计清单。
- 地铁沿用单套选择状态和默认全关。以 `network=深圳地铁`、线路 relation、站台/车站与出口的联系核对共享节点，官方线路色、出入口编号和在建状态分别登记。高铁有来源的公共出口与城市步行面相接。地图线路、3D 出入口、可通行站厅各自记录验收层级。公交样段单列车站、线路方向与信号模拟，时刻或客流缺失时保留未知。
- 纽约参考 [街块道路与交通](../ref/slop-newyork/js/road-network.js) 和 [行人路线](../ref/slop-newyork/js/pedestrian-routes.js)。武汉参考 [桥面](../ref/slop-wuhan/js/runtime/bridge-surfaces.js)、[隧道表面](../ref/slop-wuhan/js/runtime/tunnel-surfaces.js) 和 [出租车路网](../ref/slop-wuhan/js/runtime/taxi-network.js) 的职责边界。标高、坡度、车道、站位和通行规则以深圳来源为准。

### 商圈、公园和山地

- 商圈按 [27 号](27-REGION-DATA-PLAN.md) 使用道路走廊外缘和有来源的地块，跨街商圈由街块与公共连接组成。给每个面留 OSM/图纸来源、核对日期、是否开放、材质证据。购物公园先识别公共铺装、绿地、花池和建筑前场，未知硬铺装用中性外观。保留核实绿地和边界外铺装的原身份。
- 城区工程面记录控制点、原高程和过渡方法。山体和已核实公园的起伏取可追溯资料，优先在山脚、真实入口或地形分界接顺。路径与行人接触同一三角面。深南分隔带保留有来源的开口、路缘、草地与低花带，树种和株距分开标来源。坡面、林下、草地、铺装和山体轮廓各有对照点。
- 纽约参考 [中央公园和步行界面](../ref/slop-newyork/js/city-grid.js) 与 [近景树](../ref/slop-newyork/js/trees.js)。武汉参考 [按地类生成地表和岸边](../ref/slop-wuhan/js/runtime/ground.js)，山体使用深圳的高程资料。大沙河和香蜜湖内河水面另做样段，水位、岸线与地坪分别取证。

### 地标、普通建筑与商铺

- 地标先做一栋的街道层和轮廓。每个专模卡记录源 ID、相机朝向、照片日期、可对照尺寸和未知项。程序建模统一出部件、碰撞和可站表面；按已核对象接管通用楼，保留相邻楼体和架空净空。
- 普通楼用同一物理屋顶派生女儿墙和设备，去掉塔楼/裙房重复生成。源高度和足迹优先，窗格、幕墙、栏杆和阳台用贴合墙面方向的节奏。近景细节采用距离分块、预算和释放规则。按办公室、住宅、城中村和商业首层分别做样本，记录外观估计。
- 商铺先核对真实门洞、楼层和照片来源。视觉样板可用与深圳街道相符的中文店招尺度、玻璃、骑楼/雨棚或卷闸门，按样本事实取用。未核实的店名、品牌、营业和门内通行保持未知。按 Q1 检查门前净宽、脚底接触与夜间照明，保留无障碍通道。
- 纽约参考 [近景建筑细节](../ref/slop-newyork/js/building-details.js) 和 [窗墙材质](../ref/slop-newyork/js/tsl-materials.js)。武汉参考 [地标装配](../ref/slop-wuhan/js/runtime/landmark-craft.js) 和 [普通建筑](../ref/slop-wuhan/js/runtime/buildings.js)。实景外形和街道文字使用深圳样本。

### 人群、车辆与展示预算

- 行人复用纽约 `PersonRig`、`PersonCrowd`，可通行表面用深圳人行道、开口和过街。先证明行人不从绿带或车道随机穿越，再验证双向过街、排队、避让、桥上桥下和玩家输入。客流只按场景和容量模拟，记录目标人数、实际人数、生成失败和队尾。
- 车辆选深圳蓝白出租、公交和绿牌车做识别样本。现有车身与轮位仍有未提交改动，先以接手时的正式车型建立对照。沿一处路口验轮胎接触、转向、制动接管和夜间车灯。连续运行保留正常环境车流并记录堵塞原因。
- 每批先保存同机位日景、夜景、街道与俯视四类中适用的前后图。固定镜头、时段、数据哈希、种子、分辨率和视口。记录网格、实例、绘制调用、三角数和帧时。按 [10 号](10-PERF-QA.md) 做稳定窗口和正式性能验收，避免用短 HUD 截图代替。

## 并行与整合

1. 第一批可以平行推进桥上桥下复现、交通来源、商圈/公园边界审计，以及单栋地标照片对照。每个 worktree 从确认过的提交开出，或给子 agent 单独的文件范围。记录是否缺主工作区尚未提交的修改。保留现有 worktree 及其差异。
2. 先合并文件无冲突、无需数据包的专项。自动驾驶启动专项可先改 `sz-auto-drive.js` 和测试。路由、车辆控制器和入口装配随后由同一协调窗口接入。主工作区正在审查的道路/人群/树木/车辆先按主题验收，相关专项再基于结果继续。
3. `main.js`、`index.html`、`sz-data-format.js`、`tools/sz/build.py` 及共享包由协调者登记顺序。区域、地铁、地形、商铺来源清单可以并行核对。需要运行包时按 [交接第 8 节](HANDOFF.md#8-数据包提交规则2026-11-11) 统一在一个工作区重建 JSON 和 SZC1，记录报告、大小、哈希和范围外差异。运行包缺来源时仍可做纯函数回归和来源审查。
4. 交付写清基线、允许路径、源证据、已测与缺口。日常检查按 [25 号](25-FAST-CHECKS.md) 选择范围；公共几何、包契约和入口整合跑全量。QA 产物留本地 `docs/qa/<专项>/`。
5. 扩区按路线验收结果推进。能辨认城市特色且玩家走得通的样段优先；开放交通、工程高程、店铺与公园设施分别按证据更新。
